View transitions

A plain CSS transition animates one property on one element that stays put. The View Transitions API generalizes that to a whole DOM change — elements that appear, move, or leave — by snapshotting the page before & after and animating between the two frames. You don't write the animation; you make the change, and the browser tweens. system.css adds the direction helpers, a scoped mode, and the wiring so Datastar drives it.

Try it

Pick a direction, then swap the panel. Set the header's motion to Debug to watch it in slow motion — duration rides --cfg-motion.

One call — that's the whole API

Wrap any DOM change in startViewTransition. The browser freezes the old frame, runs your callback, then crossfades to the new frame. No library, no manual FLIP math. Unsupported browsers just run the callback with no animation — safe to ship today.

Raw JS 
document.documentElement.dataset.vt = "slide-left";
document.startViewTransition(() => {
  render(nextState);   // any DOM mutation
});
Datastar — the same thing, declaratively 
<button
  data-on:click__viewtransition="
    document.documentElement.dataset.vt = 'slide-left';
    $panel = next">
  Next
</button>

The __viewtransition modifier wraps the expression's DOM changes in a transition for you — this is what the Swap panel button above uses.

Directions ship as helpers

Set data-vt on <html> before you start; system.css keys the root keyframes off it.

data-vtmotion
fadeCrossfade (the default if unset)
slide-leftNew content enters from the right
slide-rightNew content enters from the left
scaleSubtle zoom crossfade
zoomPronounced zoom crossfade
isolateHold the page still — only named regions move

It obeys the motion switch — free

Duration is calc(var(--cfg-motion) * 0.28s), so data-ui-motion off → instant swap, debug → slow, and prefers-reduced-motion zeroes it.

The transition pseudo-elements live on :root, so set data-ui-motion and data-vt on <html> — not an inner wrapper — so the value reaches them.

Animate only what changes

the pattern to reach for

By default a transition captures the whole viewport as one group called root and crossfades it — so even a one-word change flashes the entire page. To scope the motion to the regions that actually change, do two things:

1Name the movers
Give each region that should animate its own view-transition-name — the .vt helper reads it from --vt. A named element becomes its own group and tweens between frames.
2Hold the rest
Set data-vt="isolate" so root — everything you didn't name — swaps with no animation. No whole-page crossfade; only your named regions move.
<html data-vt="isolate">                <!-- root holds still -->

<aside class="pg-navigation">…</aside>   <!-- unnamed → instant, no flash -->
<main>
  <article class="vt card" style="--vt: detail">   <!-- named → morphs -->
    …content that changes…
  </article>
</main>

A name must be unique per snapshot; keeping the same name on an element across the change is what links its old and new frame so it tweens instead of crossfading. Reuse a name on two visible elements and the browser skips the transition.

The title bar and tabs are unnamed, so they hold. Only the body carries --vt: scoped-body, so only it morphs when you switch. Swap under Debug motion to see the chrome stay put.

Full-page morphs, from the server

When Datastar patches the DOM from a backend datastar-patch-elements event it uses idiomorph — it walks the incoming HTML against the live DOM and mutates only the nodes that differ, leaving everything else untouched. Ask it to wrap that morph in a view transition and you get the same scoping for free: unchanged nodes don't re-render, and the regions you named animate.

SSE optionon datastar-patch-elements
useViewTransitionBoolean. true wraps the patch in startViewTransition (when the browser supports it). Default false.
viewTransitionSelectorA CSS selector naming the element the transition should center on — the scope hint for the patch.
Server sends (SSE) 
event: datastar-patch-elements
data: useViewTransition true
data: viewTransitionSelector #board
data: mode inner
data: selector #board
data: elements <div id="board">…new cards…</div>
Client already scoped it 
<html data-vt="isolate">
<div id="board" class="vt" style="--vt: board">
  <!-- idiomorph swaps only the cards that changed;
       #board is a named group, so just it morphs -->
</div>

So the two halves meet: the server decides a morph should transition (useViewTransition); the stylesheet decides what actually moves (a name + isolate). You can fat-morph a whole page and still animate a single card.

Persistent app shell

Add data-vt-shell to a .page and every chrome slot gets a stable name, so on any navigation the header/nav/aside/footer are their own groups and hold while only .pg-main morphs — the app-shell form of isolate, named once.

<div class="page" data-vt-shell>
  <header class="pg-header">…</header>   <!-- holds -->
  <nav class="pg-navigation">…</nav>    <!-- holds -->
  <main class="pg-main">…</main>        <!-- morphs -->
</div>

Across separate pages, zero JS

For real multi-page navigations, one at-rule opts every same-origin load into a transition — no script. Pair it with data-vt-shell and the shell persists across page loads.

@view-transition { navigation: auto; }

Left off by default in system.css so multi-page sites opt in deliberately.

What the stylesheet defines

Root pseudo-elements + keyframes keyed to data-vt, the .vt name hook, and the shell opt-in:

::view-transition-group(*) { animation-duration: calc(var(--cfg-motion) * 0.28s); }
::view-transition-old(root) { animation-name: vt-fade-out; }   /* default */
::view-transition-new(root) { animation-name: vt-fade-in; }
:root[data-vt="slide-left"]::view-transition-old(root) { animation-name: vt-out-left; }
/* …slide-right, scale, zoom… */
:root[data-vt="isolate"]::view-transition-old(root),
:root[data-vt="isolate"]::view-transition-new(root) { animation: none; }  /* hold root */

.vt { view-transition-name: var(--vt, none); }                 /* name a mover */
.page[data-vt-shell] > .pg-main { view-transition-name: pg-main; }  /* + each slot */

Support: Chromium (same- & cross-document), Safari (recent), Firefox (partial) — and a graceful instant swap everywhere else. Only one transition runs at a time. Element-scoped element.startViewTransition() is Chromium-only for now, so isolate + names is the portable way to scope today.
