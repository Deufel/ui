View transitions

You don't write the animation — you make the DOM change, and the browser tweens the before and after for you. With Datastar that's two things: wrap the change so the browser snapshots it, and name the element that should move. Everything else on this page is elaboration on those two moves.

The whole thing, in two moves

1Wrap the change
Add __viewtransition to the Datastar action that changes the DOM. It runs your change inside document.startViewTransition() — the browser freezes the old frame, applies the change, and crossfades to the new one. No library. 
<button data-on:click__viewtransition="$open = true">
2Name what should move
Give the element a view-transition-name (the .vt helper reads it from --vt). Named elements morph independently; everything unnamed is captured together as root. 
<article class="vt" style="--vt: hero">…</article>
That's the simplest correct usage — and it's all frontend, so it works on static hosting (GitHub Pages) with no server. You do not need data-vt, isolate, or a build step for the common case. Those are the extras further down.

What actually animates

This is the one rule that explains everything — including why some changes move the whole page and some move only one box:

rooteverything unnamed
The whole viewport, minus the named elements, captured as one group. Animates only if something in it changed — or if you force it with a data-vt direction.
namedeach .vt element
Pulled out of root into its own group and matched old→new by name. Morphs (position, size, content) when that element changed.
what you seegroups that differ
A group only animates when its before-picture ≠ its after-picture. Unchanged groups hold perfectly still, even mid-transition.

So if you change one named region and nothing else, only that region moves — root is identical before and after, so it just holds. That is the effect you want, and it's the default. You reach for the extras below only to override this: to animate the whole page on purpose, or to freeze root when it did change.

Demo · morph one element

just wrap + name

One element with a stable name. Clicking only changes its size — so the browser tweens its old box into its new box. No data-vt, no isolate; the rest of the page holds because nothing else changed. Try it under Debug motion.

<div class="growbox"                       <!-- has view-transition-name: growbox -->
     data-class:big="$grow"                <!-- .big just changes its width/height -->
     data-on:click__viewtransition="$grow = !$grow">
  grow / shrink
</div>

Demo · scale off & on

enter / leave

When a named element appears or leaves (here via data-show), the browser plays its enter/leave animation. This one is pointed at zoom, so it scales down as it goes and pops up as it returns — exactly the "scales down and disappears" you asked about.

poof
/* the element's group is named `poof`; assign the enter/leave keyframes to it */
::view-transition-old(poof) { animation-name: vt-out-zoom; }  /* scales down + fades */
::view-transition-new(poof) { animation-name: vt-in-zoom;  }  /* scales up on return */
<button data-on:click__viewtransition="$poof = !$poof">Toggle</button>
<div class="vt" style="--vt: poof" data-show="$poof">poof</div>

Set data-vt on <html> to give root — the whole page — a direction instead of a plain crossfade. Pick one and swap; the panel below plays it. (In a real app the entire viewport does this on a route change; here the keyframes are scoped to the demo panel so you can watch each one.)

Name it reactively

A name must be unique among visible elements per snapshot. To make one card the mover only when it's the active one, toggle the name with data-style — the free equivalent of Datastar's Pro data-view-transition.

<div class="vt"
     data-style="{'--vt': $open === id ? 'hero' : 'none'}">

Give the same name to the outgoing card and the incoming detail and the browser morphs one into the other.

Where __viewtransition lives

The modifier wraps the DOM change for any of these Datastar triggers — pick whichever fires your change:

triggerfires on
data-on:click__viewtransitiona user event
data-init__viewtransitionelement enters the DOM
data-on-interval__viewtransitiona timer
data-on-intersect__viewtransitionscrolls into view

Fetching content — what works on GitHub Pages

A @get('/fragment.html') is a plain GET, so a static file is your "server" — Datastar fetches it and morphs it in (idiomorph, so only changed nodes move). Two honest caveats on transitioning that:

Frontend swaps → simpleA change you drive with signals (show/hide, class, data-style) is synchronous, so __viewtransition wraps it cleanly. This is the path to prefer on static hosting.
Async fetch → needs the server__viewtransition can't wrap a fetch that resolves later. The clean way to transition a morph is the SSE flag useViewTransition true — but that needs a streaming backend, which a static file can't be.
Practical recipe for a static site: fetch the data into a hidden region with @get, then reveal it with a signal change wrapped in __viewtransition and named with .vt. You get the morph, and the "server" is just a file. When you later move to a streaming backend, add useViewTransition true to the patch and the same names light up automatically.

Persistent app shell

Add data-vt-shell to a .page and every chrome slot gets a stable name — so on any navigation the header/nav/footer hold and only .pg-main morphs. Isolate, but named once for the whole shell.

<div class="page" data-vt-shell> … </div>

Real page-to-page, zero JS

For multi-page navigations, one at-rule opts every same-origin load into a transition — works on plain static hosting.

@view-transition { navigation: auto; }

Off by default in system.css so you opt in deliberately.

Motion is governed for you. Every transition's duration is calc(var(--cfg-motion) * 0.28s), so data-ui-motion off → instant, debug → slow, and prefers-reduced-motion zeroes it. Set data-ui-motion and data-vt on <html> — the transition pseudo-elements live on :root.

Support: Chromium (same- & cross-document), Safari (recent), Firefox (partial) — with a graceful instant swap everywhere else. Only one transition runs at a time. Element-scoped element.startViewTransition() is Chromium-only for now, so naming + isolate is the portable way to scope today.
